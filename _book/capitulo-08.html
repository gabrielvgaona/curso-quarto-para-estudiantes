8  Git y GitHub para trabajo colaborativo

8.1 ¿Por qué control de versiones?

Seguramente has tenido archivos con nombres como:

informe_final.docx
informe_final_v2.docx
informe_final_v2_corregido.docx
informe_final_DEFINITIVO.docx
informe_final_DEFINITIVO_ahora_si.docx

Esto es un sistema de “control de versiones” manual, y tiene problemas evidentes:

  • No sabes exactamente qué cambió entre versiones.
  • Cuando trabajan varias personas, hay conflictos al combinar cambios.
  • Es difícil volver atrás a una versión anterior específica.

Git resuelve estos problemas. Es un sistema de control de versiones que registra cada cambio que haces en tus archivos, quién lo hizo, cuándo y por qué.

GitHub es una plataforma en la nube que almacena tus repositorios Git y facilita la colaboración con otros.

8.2 Instalar y configurar Git

8.2.1 Instalación

  • Windows: descarga desde git-scm.com.
  • macOS: ejecuta xcode-select --install en la Terminal, o descarga desde git-scm.com.
  • Linux (Ubuntu/Debian): ejecuta sudo apt install git en la terminal.

8.2.2 Configuración inicial

Abre la Terminal de RStudio y ejecuta estos comandos (reemplaza con tus datos):

git config --global user.name "Tu Nombre"
git config --global user.email "tu.correo@ikiam.edu.ec"

Esto le dice a Git quién eres, para que cada cambio que registres quede asociado a tu nombre.

8.2.3 Verificar la configuración

git config --list

8.3 Conceptos fundamentales

8.3.1 Repositorio

Un repositorio (o repo) es una carpeta cuyo historial de cambios está rastreado por Git. Tu proyecto de Quarto será un repositorio.

8.3.2 Los tres estados de Git

Git maneja tus archivos en tres áreas:

  1. Directorio de trabajo: tus archivos tal como los ves en tu computadora.
  2. Área de preparación (staging area): los cambios que seleccionaste para el siguiente commit.
  3. Repositorio: el historial permanente de cambios (commits).

8.3.3 Commit

Un commit es una “foto” del estado de tus archivos en un momento dado. Cada commit tiene:

  • Un mensaje que describe qué cambiaste.
  • Un autor (tú).
  • Una fecha y hora.
  • Un identificador único (hash).

8.3.4 Push y pull

  • Push: enviar tus commits locales a GitHub (subir cambios).
  • Pull: traer los commits de GitHub a tu computadora (descargar cambios de tus compañeros).

8.4 Crear una cuenta en GitHub

  1. Ve a github.com y crea una cuenta gratuita.
  2. Usa tu correo institucional de Ikiam si es posible.
  3. Opcionalmente, solicita el GitHub Student Developer Pack para obtener beneficios adicionales.

8.5 Flujo de trabajo con RStudio

RStudio tiene integración nativa con Git. No necesitas usar la terminal para las operaciones básicas.

8.5.1 Crear un nuevo proyecto con Git

  1. File > New Project… > New Directory > Quarto Project.
  2. Marca la casilla “Create a git repository”.
  3. Dale un nombre y elige la ubicación.

8.5.2 Conectar con GitHub

Desde la Terminal de RStudio:

# Crear el repositorio en GitHub primero (desde github.com)
# Luego conectar tu proyecto local:
git remote add origin https://github.com/tu-usuario/tu-repositorio.git
git branch -M main
git push -u origin main
Alternativa más sencilla

Si prefieres evitar la terminal, puedes crear el repositorio directamente en GitHub y luego clonarlo en RStudio: File > New Project… > Version Control > Git y pegar la URL del repositorio.

8.5.3 El flujo diario

Una vez configurado, tu flujo de trabajo diario es:

  1. Pull — antes de empezar a trabajar, descarga los últimos cambios.
  2. Editar — trabaja en tus archivos .qmd normalmente.
  3. Stage — selecciona los archivos modificados en el panel Git de RStudio.
  4. Commit — escribe un mensaje descriptivo y confirma los cambios.
  5. Push — sube tus cambios a GitHub.

8.5.4 El panel Git de RStudio

En RStudio, el panel Git (generalmente en la esquina superior derecha) muestra:

  • Archivos modificados (ícono azul M).
  • Archivos nuevos (ícono verde ?).
  • Archivos eliminados (ícono rojo D).

Para hacer un commit:

  1. Marca las casillas de los archivos que quieres incluir (stage).
  2. Haz clic en Commit.
  3. Escribe un mensaje descriptivo (ver sección siguiente).
  4. Haz clic en Commit, luego en Push.

8.6 Escribir buenos mensajes de commit

Un buen mensaje de commit es breve pero informativo:

✗ Mal ✓ Bien
“cambios” “Agregar gráfico de caudal mensual al cap. 3”
“actualización” “Corregir ecuación de Manning en la sección 2.1”
“fix” “Arreglar error en la lectura del CSV de temperatura”
“asdfgh” “Agregar referencias bibliográficas de hidrología”

8.7 Colaborar en un repositorio compartido

Para el proyecto integrador, trabajarán en equipo en un mismo repositorio.

8.7.1 Configuración del equipo

  1. Un miembro del equipo crea el repositorio en GitHub.
  2. Va a Settings > Collaborators y agrega a los demás miembros por su nombre de usuario de GitHub.
  3. Cada miembro clona el repositorio en su computadora.

8.7.2 Evitar conflictos

La estrategia más simple para evitar conflictos cuando trabajan varias personas:

  1. Comunicarse antes de editar: “Yo voy a trabajar en el capítulo de resultados.”
  2. Dividir el trabajo por archivos: cada persona trabaja en secciones diferentes.
  3. Pull antes de push: siempre descargar los últimos cambios antes de subir los tuyos.
  4. Commits pequeños y frecuentes: es más fácil resolver conflictos en cambios pequeños.

8.7.3 ¿Qué pasa si hay un conflicto?

Un conflicto ocurre cuando dos personas modifican la misma línea del mismo archivo. Git marca la zona conflictiva así:

<<<<<<< HEAD
Tu versión del texto
=======
La versión de tu compañero
>>>>>>> origin/main

Para resolverlo:

  1. Abre el archivo en conflicto.
  2. Decide qué versión conservar (o combínalas).
  3. Elimina las marcas de conflicto (<<<<<<<, =======, >>>>>>>).
  4. Guarda, haz commit y push.
La mejor solución es prevenir

Si cada miembro trabaja en archivos distintos, los conflictos son raros. Divídanse el trabajo claramente.

8.8 El archivo .gitignore

Hay archivos que no deberían subirse a GitHub: archivos temporales, datos muy grandes, credenciales, etc. El archivo .gitignore le dice a Git qué ignorar:

# Archivos generados por Quarto
_site/
_freeze/
.quarto/

# Archivos de RStudio
.Rproj.user/
.Rhistory
.RData

# Archivos del sistema
.DS_Store
Thumbs.db

RStudio crea un .gitignore básico automáticamente al crear un proyecto con Git.

8.9 Actividad autónoma

  1. Si no lo has hecho, crea tu cuenta en GitHub.
  2. Crea un nuevo repositorio en GitHub (público, con README).
  3. Clónalo en RStudio: File > New Project > Version Control > Git.
  4. Crea un archivo prueba.qmd con un título, tu nombre y un párrafo breve.
  5. Renderiza el documento.
  6. Haz al menos 3 commits con mensajes descriptivos:
    • Commit 1: “Crear documento inicial”
    • Commit 2: (agrega contenido)
    • Commit 3: (modifica algo)
  7. Push tus cambios a GitHub.
  8. Verifica en GitHub que tus archivos y el historial de commits aparecen correctamente.
